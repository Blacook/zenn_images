## 核メッセージ

最終課題が終わったあと、Bootcamp の核メッセージがもう一度スクリーンに出された。

> **Most AI system failures aren't model problems, but prompt, agent architecture, and tool design problems.**

このメッセージが 2 日間ずっと地下水脈のように通っていたのだ、ということが、9 章分を書き終えたいまになってようやく腹落ちする。新しいモデルが出るたびに能力は伸びるが、本番でエージェントが壊れる原因の大半は「モデルが弱いから」ではない。

- プロンプトが役割と使用義務を明示していない
- tool description が許可値や挙動を伝えていない
- tool 実装がエラー時に文脈を返さない
- eval が仕様を表現していない
- context に distractor が混じっている

の組み合わせだ。これは観察された経験則というより、エンジニアリング上の事実として扱える指針として教えられた。「モデルを上位に差し替える」より先に直すべき場所が、ここに 5 つ並んでいる。

## エージェントエンジニアリングの8 つのレイヤー

連載 8 章分の内容を踏まえると、エージェントエンジニアリングという仕事は **独立した各レイヤーの集合体** として見えてくる。各レイヤーは独立に読めるが、本番システムを設計するときは、**規律の集合体** として、これらを 1 工程として並べて使う必要がある。

| レイヤー                | 何を扱うか                                          | 主に扱った章 |
| ----------------------- | --------------------------------------------------- | ------------ |
| 活用（Tooling）         | Claude Code を「手の延長」に変える                  | 02           |
| 基盤構築（Scaffolding）     | CLI / API / MCP / Skills / Plugins の選び分け       | 03           |
| チューニング（Prompting）     | プロンプト診断と評価駆動の修復                      | 04           |
| 原因診断（Diagnosis） | system prompt / tool definition / trace の読み方    | 05           |
| 評価（Eval）            | 数字でエージェントを定義し、PM を巻き込む           | 06           |
| コスト最適（Inference）     | レイテンシとコストの p99 設計と prompt caching      | 07           |
| 文脈（Context）         | コンテキストを有限資源として運用する                | 08           |
| 合成（Agent Build）     | 上記すべてのレイヤーを 1 工程として並べる           | 09           |

## 3 つの takeaway はどこで具体化されたか

第 1 章の冒頭で立てた 3 つの takeaway は、各章を経て次の場所に着地した。

- **#1 マルチエージェント評価は未解決** ── 第 6 章で eval を PM と回す具体的なフローまで降り、grader の階層と非決定性ハンドリングまで扱った。
- **#2 Context Engineering は独立した規律** ── 第 8 章で context rot、tool result clearing、compaction、memory tool として運用論まで踏み込んだ。
- **#3 IT の役割は根本的に変わる** ── 第 9 章で「モデルを呼び出すシステムを組み立てる仕事」から「eval で挙動を定義し、3 層で defense を組み、未知入力に対する堅牢性を設計判断として切る仕事」への移行として着地した。

3 つの takeaway はそれぞれ別の章で具体化されたが、最後はひとつのシンプルな考えに収束する ── エージェントエンジニアリングという仕事は、"モデルの進化を待つ仕事ではない"、ということだ。

## Workshop 全体の質疑応答

休憩時間や最終 Q&A の場で投げかけられた問いは、技術トピックを越えて「これからの働き方そのもの」を問うものだった。会場で交わされた 5 つの質疑を、それぞれの回答とともに残しておく。

### Q1. 人間がいま伸ばすべき能力は何か

問：AI が業務の中核に入ってくる時代に、コンサルタント／エンジニアが優先して伸ばすべき能力は何か。

答えとして挙がったのは大きく 4 つ

- **コミュニケーション能力** — どの時代でも変わらず最重要で、AI 時代にもこれだけはむしろ価値が上がる
- **「深く潜る力 × 横断する力」の両立** — 特定領域を技術的に深掘りできることに加え、システム全体を横串で見られる能力
- **オーケストレーション理解** — 多くの人が苦手とするが、これからの差別化要素
- **T字型（深さと広さの切替）** — CIO レベルの俯瞰と現場レベルの深掘りを行き来できること

ホストはここに **Great Equalization（大いなる平準化）** という言葉を補足した。エンジニア → アーキテクト → コンサルタントへのジャンプが、これほど短くなった時代はない、と。AI ツールによって役割の越境が手元で可能になっているという指摘で、これは第9章で書いた「IT の役割の根本的な変化」と地続きの話だと感じた。

### Q2. 新モデルのリリース計画は

問：Mythosのパブリックに公開予定はあるか。

回答は「**責任あるリリース方針**を優先しており、慎重に進めている」というものだったが、続いて出た一言のほうが印象に残った ── 「ただし**ユースケースの 90〜95% は、既存のツール／モデルで対応可能**」。新モデルを待つより、今あるもので作り始めるべきだ、という講師のスタンスは、Workshop 全体を通じて何度も繰り返された。第2章の Claude Code 演習も、第9章の RFP エージェントも、特別なモデルを使ったわけではない ── 既存の Opus / Sonnet / Haiku で十分に到達できるものだった。

### Q3. AI 時代の意思決定について

問：年長者が AI に意思決定を委ねるシーンを見るようになったのをどう捉えればいいか。

講師の答えは二面的だった。一方で AI は **認知的・感情的な余力** を解放してくれる ── 自分がやりたくない冗長なタスクをオフロードできるのは大きな恩恵だ。しかし他方で、若い世代がまだ「思考力を養う 2〜30年」を経ていない点への懸念は残る。考える筋肉を使う前に、考える行為そのものを外部化してしまったとき、彼らの思考力はどう育つのか。これは答えが出ている領域ではなく、これから研究者が時間をかけて答えるべきテーマだ、という姿勢で締められた。

### Q4. この2日間のアウトカム — パートナーが持ち帰るべきもの

問：我々パートナーは、この2日間のトレーニングから何を持ち帰るべきか。

答えとして強調されたのは、まず「**この部屋で出た議論・アイデアは、数週間〜数ヶ月後に実際にプロダクトとして出荷される**」という事実だった。これは比喩ではなく、彼らの開発速度を踏まえれば文字通りそうなる、と。そのうえで、パートナーに求められるアクションは次の 3 つに集約された。

- 積極的に Anthropic に**フィードバック・リーチアウト**する
- **エージェントを実際に作って試す**
- 顧客の声を吸い上げてプロダクトサイドに渡す

これはいわゆる「ベンダーとパートナー」という関係性というより、「同じプロダクトを一緒に育てる側」として扱われている感覚があった。

### Q5. クライアントが AI を使い始めた時代の、コンサルの売上

問：クライアントが自分で AI ツールを使いこなし始めている。コンサルの売上をどう守るのか。

回答は明快だった。第一に「**良いエージェントを作るのは簡単ではない**」 ── 見た目を作るのと、本当に問題解決するエージェントを作るのは別物だ、という事実。第二に、コンサルタントには **head start（先行者利益）** がある。他者はいずれ追いつくが、いまエージェント構築スキルを磨いている人は明確にリードしている。第三に、求められる姿勢として **Reinvention（自己変革）** と **Proactivity（先回り提案）** の 2 つが繰り返された。AI 企業／AI ソフトウェアを相手にしていても、提案を出し続けることが重要だ、という補足が添えられていた。

### 回答内容に共通するメッセージ

Workshop 全体を通底していたメッセージは ── **役割の境界が崩れる時代に、深さと広さを両立し、待たずに作り始める**、ということに尽きた。Q1 が深さ × 広さを、Q2 が今あるもので作り始める姿勢を、Q4 と Q5 が proactivity を、それぞれ別角度から指していた。ひとつひとつは聞き慣れた話かもしれないが、2日間分の議論の最後にまとめて投げ返されると、一貫した姿勢として再確認することができた。

## すぐに実行すべきアクション提案

次のスプリントから始められる具体的なアクションを 3 つ提示して終わりたい。

1. **自分が今関わっているエージェントに、Pressure Test 5 パターンのうち最も弱そうな 1 つを当ててみる**。Hallucination trap か False-premise が手薄なケースが多いはず。1 ケース分の入力を書いてエージェントに通すだけで、defense の穴が露わにできる。
2. **system prompt / tool description / tool 実装が、3 層責務モデルに照らしてどの層が薄いかを棚卸ししてみる**。抜け落ちている層に”単一責任”を意識して 1 行ずつ定義を埋めるだけで、エージェントの振る舞いは別物になる。
3. **Claude に「この eval harness を作って」と問いかける一文から始めてみる**。assertion は 5 つで十分です。PRD 段階で PM・SE と一緒に書き、エージェントの責務範囲を eval として固定する。
