サンフランシスコで Anthropic の Partner Bootcamp という2日間の集中プログラムに参加してきた。会場の空気の濃さもあるけれど、何より「エンタープライズで AI をどう捉えるか」という自分のメンタルモデルが、行く前と帰ってきた後で大きく変わった。技術的なトピックを順に追ったというより、長く感じていた気掛かりな点を一つひとつ言語化していくような2日間だった。

読み返したときに「あの2日間で何を受け取ってきたのか」を自分自身が忘れないように、そして同じプロジェクト、組織、会社、業界で仕事をしている方に向けて「ここまでは確実に共有しておきたい」という温度感で書いていく。

## この連載をどう読むか

Bootcamp で扱われたトピックを、自分なりに再配列して全10章の Zenn Book にまとめた。本章はその入口にあたる。各章にはハンズオン用の公式リポジトリ [Basecamp-Exercises](https://github.com/victorsteeb/Basecamp-Exercises.git) の Notebook へのポインタを置いてある。手を動かしながら読むのを推奨するが、概念だけ追いかけても1章単位で読めるように構成した。順番通り読まなくてもよい構成で、たとえば「Eval の話だけ知りたい」なら第6章、「Context Engineering を腰を据えて学びたい」なら第8章から入って構わない構成となっている。

## 2日間のカリキュラム俯瞰

プログラムは Day1 と Day2 に分かれていた。Day1 のテーマは「確信をもって作る（Building with Confidence）」、Day2 は「規律をもってスケールさせる（Scaling with Rigor）」。この対比そのものが、Anthropic がエンタープライズ AI をどう位置づけているかを物語っている気がする。

Day1（Building with Confidence）で扱われた4セッション。

- 在庫管理アプリを題材にした Claude Code workshop
- Developer Platform — CLI / API / MCP / Skills / Plugins の選び分けと Messages API の中身
- Prompt Rescue（動かないプロンプトを診断し、回復させるワーク）
- 本番システムにおける AI の故障モードを切り分けるフレームワーク

Day2（Scaling with Rigor）の4セッション。

- Eval 設計 — 雰囲気評価（vibe check）から、測れる評価へ
- スケール時のレイテンシとコスト最適化
- Context Engineering の深掘り（個人的にいちばん刺さった）
- すべてを使い切る Agent Build Hackathon

Day1 で「とにかく動くものを作れる」感覚を全員に持たせてから、Day2 で「その動くものをどう測り、どう運用に乗せるか」へ視点を引き上げる。

## 2日間の核メッセージ

セッションが切り替わるたびに、講師たちは少しずつ言い回しを変えながら同じことを繰り返していた。後から振り返ると、講義の核は以下の一文に集約できる。

> Most AI system failures aren't model problems, but prompt, agent architecture, and tool design.

事前にAnthropic提供の別のコースで知識としては知っていたが、この文がなぜここまで強調されるのか、その本質は理解できていなかった。ただ、Prompt Rescue のセッションで「動かないプロンプト」を実際に渡され、それを段階的に直していく作業をしていくうちに、自分のなかで腑に落ちた瞬間があった。

これまで「精度が足りない」と感じた局面で、自分はかなりの確率で「より上位のモデルに変えればよくなるはずだ」と考えていた。けれど現地で実際にプロンプトとツール定義を解剖していくと、改善余地のほとんどはモデルではなく、その手前の「指示の与え方」「Agent の組み立て方」「ツールの説明文の書き方」の側にあった。モデルが悪いのではなく、こちらの伝え方が悪い。この当たり前のことを、”言葉”ではなく”感覚”として身につけることができた2日間だったと言ってもいい。

## 特に印象に残った3つのこと

### 1. マルチエージェント評価は、ほとんどのチームで未解決のままだ

これは Bootcamp で最も強く揺さぶられた論点である。シングルプロンプトの評価であれば、ある程度の知見が業界に蓄積されている。だがエージェントが複数連携し、ツールを呼び、状態を持って動くシステムを「何をもって良いとするか」となると、急に手探りになる。

現地のセッションで提示された評価フレームワークは、outcome quality（最終アウトプットの品質）だけを見るのではなく、reasoning transparency（思考の透明性）、tool-use reliability（ツール利用の安定性）、failure recovery（失敗からの回復力）という観点を並列に置いていた。この4つを別軸として捉えると、「精度は高いが何をしているか分からないエージェント」と「精度は中くらいだが挙動が説明できるエージェント」のどちらを本番に出すべきかという議論ができるようになる。これまで自分は前者を黙って許容してきた節があり、ここは現場に戻ってから真っ先に試したい。

### 2. Context Engineering は nice-to-have ではなく、これが規律だ

Day2 の Context Engineering 回は、個人的にいちばん刺さったセッションだった。凡庸な AI システムと、信頼して任せられる AI システムの差は、多くの場合「どの情報を、どのような形で、いつ与えるか」という設計の質で決まる。プロンプトエンジニアリングは入口にすぎず、本当のレバレッジはコンテキストの設計にある、というのが現地で繰り返されたメッセージだった。

長く詰め込めば安全、というのは過去の発想で、むしろ長いコンテキストは忠実性と検索精度を下げる。だからこそ「何を残し、何を削り、どこで圧縮し、どこで外部メモリに逃がすか」を一つの工学規律として扱う必要がある。これは流行りの技法というより、AI システムを扱う以上、避けて通れない基礎体力に近い。この章を学んだあと、自分のなかで「プロンプトを書く」という言葉の指す定義を広げることができた。

### 3. この時代の IT の役割は、根本的に変わりつつある

最後の takeaway はもう少し業界寄りの話になる。AI が業務の中核に入ってくる時代、IT に求められる役割はもはや単なる技術導入のインテグレータではなくなりつつある。「信頼でき、説明でき、監査できる知的システム」を設計し、運用に乗せ、社会に対して責任を負うアーキテクトであること。Bootcamp の議論の端々で、この方針が言及されていた気がする。

これは深い責任だと思う。モデルを呼び出すだけのシステムであれば誰でも作れる時代に、「なぜこの判断が出たのか」を説明し、「次にこう壊れたら、こう気づける」と保証することは、技術と倫理の両方に重点を置くことである。業界として真剣に受け止めるべきテーマで、自分自身も腰を据えて取り組んでいきたい。

## Tips

カリキュラム本体と同じくらい価値があったのが、各セッション後の質疑応答の時間だった。とくに印象に残ったやり取りを、メモ的に短く触れておく。それぞれの詳細は該当する章で深掘りする。

- **Agent as Advisor 戦略** — Sonnet を主役にプロセスを駆動し、Opus は詰まったときの相談役として呼び出す。直感に反するこの構成のほうが、コストも品質も安定する場面が多いという。詳細は第3章で。
- **モデルアップデートと Eval の関係** — 新モデルへの乗り換えは、Eval スイートを"防衛線"として持っていない限り、リリースリスクに直結する。第6章で。
- **LLM-as-Judge のモデル選定** — Judge は強ければ強いほどよい、という直感は誤り。判定タスクの性質に応じて Haiku/Sonnet/Opus を使い分ける視点が紹介された。第6章で。
- **他のSDK との比較** — フレームワークの新しさで選ぶのではなく、何を制御したいかを起点に SDK を選ぶ。第3章で扱う。

## Workshop 全体に流れた問い

各セッション固有の Q&A とは別に、休憩時間や最終 Q&A の場で workshop 全体に対して投げかけられた問いがあった。キャリア・市場・姿勢にまたがるもので、現地で参加者全員が肌で感じていたテーマだったように思う。ここでは予告として短く触れ、詳細は[第10章](10-conclusion)で深掘りする。

- **Q1. 人間がいま伸ばすべき能力は何か** — コミュニケーション × T字型 × オーケストレーション理解。エンジニアとアーキテクトの距離が極端に短くなった時代（**Great Equalization**）に、何を深掘りし何を横串で持つか。
- **Q2. 新モデルを待つべきか** — 答えは「待たない」。ユースケースの 90〜95% は既存のモデル／ツールで解ける。今あるもので作り始めること。
- **Q3. AI 時代の意思決定** — AI は認知的・感情的な余力を解放する。一方で「若い世代が思考力を養う 2〜30年を経ていない」点への懸念は、今後の研究テーマとして開かれている。
- **Q4. この2日間のアウトカム** — この部屋で出た議論は数週間〜数ヶ月後にプロダクトに反映される。パートナーに求められるのはフィードバックと、エージェントを実際に作って回すこと。
- **Q5. クライアントが AI を使い始めた時代のコンサルの売上** — 見た目を作るのと、本当に問題を解くエージェントを作るのは別物。head start を持つコンサルタントには **Reinvention** と **Proactivity** が求められる。

## 現地での会話の価値

最後にひとつ書き残しておきたいのは、現地で交わした会話内容のリアルさだった。同テーブルに座っていた参加者は、まったく違う業界で似たような悩みを抱えていて、休憩時間に「うちでは Eval をどのように実施しているか」や「System Promptを書く際に何に気をつけているか」という具体的な話を交換できた。

Bootcamp のカリキュラムは丁寧に設計されているが、それでも持ち帰ったものの半分くらいは、現地での会話のなかから受け取った気がする。同じ時代に、同じテーマで、同じくらいの真剣さで悩んでいる人たちと2日間を過ごす経験そのものが、このプログラムの価値の少なくとも半分を占めていた、というのが帰国してからの率直な感想である。
