サンフランシスコで Anthropic の Partner Bootcamp という2日間の集中プログラムに参加してきた。会場の空気の濃さもあるけれど、何より「エンタープライズで AI をどう捉えるか」という自分のメンタルモデルが、行く前と帰ってきた後で別物になっている。技術的なトピックを順に追ったというより、長く感じていた違和感を一つひとつ言語化していくような2日間だった。

帰国してすぐ羽田で同僚に話したら30分では足りなかった。だからこの連載を書いている。読み返したときに「あの2日間で何を受け取ってきたのか」を自分自身が忘れないように、そして隣の席で同じ仕事をしている同業の方に「ここまでは確実に共有しておきたい」という温度感で書いていく。

## この連載をどう読むか

Bootcamp で扱われたトピックを、自分なりに再配列して全9章の Zenn Book にまとめた。本章はその入口にあたる。各章にはハンズオン用の公式リポジトリ [Basecamp-Exercises](https://github.com/victorsteeb/Basecamp-Exercises.git) の Notebook へのポインタを置いてある。手を動かしながら読むのを推奨するが、概念だけ追いかけても1章単位で読めるように構成した。

順番通り読まなくてもよい。たとえば「Eval の話だけ知りたい」なら第6章、「Context Engineering を腰を据えて学びたい」なら第8章から入って構わない。本章は地図に近い。

## 2日間のカリキュラム俯瞰

プログラムは Day1 と Day2 に明確に分かれていた。Day1 のテーマは「確信をもって作る（Building with Confidence）」、Day2 は「規律をもってスケールさせる（Scaling with Rigor）」。この対比そのものが、Anthropic がエンタープライズ AI をどう位置づけているかを物語っている気がする。

Day1（Building with Confidence）で扱われた4セッション。

- 在庫管理アプリを題材にした Claude Code workshop
- Developer Platform — CLI / API / MCP / Skills / Plugins の選び分けと Messages API の中身
- Prompt Rescue（動かないプロンプトを診断し、回復させるワーク）
- 本番システムにおける AI の故障モードを切り分けるフレームワーク

Day2（Scaling with Rigor）の4セッション。

- Eval 設計 — 雰囲気評価（vibe check）から、測れる評価へ
- スケール時のレイテンシとコスト最適化
- Context Engineering の深掘り（個人的にいちばん刺さった）
- すべてを使い切る Agent Build Hackathon

Day1 で「とにかく動くものを作れる」感覚を全員に持たせてから、Day2 で「その動くものをどう測り、どう運用に乗せるか」へ視点を引き上げる。設計者の意図が透けて見える組み立てだった。

## 2日間の底流にあった核メッセージ

セッションが切り替わるたびに、講師たちは少しずつ言い回しを変えながら同じことを繰り返していた。後から振り返ると、その通奏低音はこの一文に集約できる。

> Most AI system failures aren't model problems, but prompt, agent architecture, and tool design.

この文がなぜここまで強調されるのか、最初は正直ピンとこなかった。ただ、Prompt Rescue のセッションで「動かないプロンプト」を実際に渡され、それを段階的に直していく作業をしていくうちに、自分のなかで腑に落ちた瞬間があった。

これまで「精度が足りない」と感じた局面で、自分はかなりの確率で「より上位のモデルに変えればよくなるはずだ」と考えていた。けれど現地で実際にプロンプトとツール定義を解剖していくと、改善余地のほとんどはモデルではなく、その手前の「指示の与え方」「Agent の組み立て方」「ツールの説明文の書き方」の側にあった。モデルが悪いのではなく、こちらの伝え方が悪い。この当たり前のことを、講義室で何度も突きつけられた2日間だったと言ってもいい。

## 持ち帰った3つのこと

### 1. マルチエージェント評価は、ほとんどのチームで未解決のままだ

これは Bootcamp で最も強く揺さぶられた論点である。シングルプロンプトの評価であれば、ある程度の知見が業界に蓄積されている。だがエージェントが複数連携し、ツールを呼び、状態を持って動くシステムを「何をもって良いとするか」となると、急に手探りになる。

現地のセッションで提示された評価フレームワークは、outcome quality（最終アウトプットの品質）だけを見るのではなく、reasoning transparency（思考の透明性）、tool-use reliability（ツール利用の安定性）、failure recovery（失敗からの回復力）という観点を並列に置いていた。この4つを別軸として捉えると、「精度は高いが何をしているか分からないエージェント」と「精度は中くらいだが挙動が説明できるエージェント」のどちらを本番に出すべきかという議論ができるようになる。これまで自分は前者を黙って許容してきた節があり、ここは現場に戻ってから真っ先に試したい。

### 2. Context Engineering は nice-to-have ではなく、これが規律だ

Day2 の Context Engineering 回は、個人的にいちばん刺さったセッションだった。凡庸な AI システムと、信頼して任せられる AI システムの差は、多くの場合「どの情報を、どの形で、いつ与えるか」という設計の質で決まる。プロンプトエンジニアリングは入口にすぎず、本当のレバレッジはコンテキストの設計にある、というのが現地で繰り返されたメッセージだった。

長く詰め込めば安全、というのは過去の発想で、むしろ長いコンテキストは忠実性と検索精度を下げる。だからこそ「何を残し、何を削り、どこで圧縮し、どこで外部メモリに逃がすか」を一つの工学規律として扱う必要がある。これは流行りの技法というより、AI システムを扱う以上、避けて通れない基礎体力に近い。この章を学んだあと、自分のなかで「プロンプトを書く」という言葉の指す範囲が静かに広がった。

### 3. この時代の IT の役割は、根本的に変わりつつある

最後の takeaway はもう少し業界寄りの話になる。AI が業務の中核に入ってくる時代、IT に求められる役割はもはや単なる技術導入のインテグレータではなくなりつつある。「信頼でき、説明でき、監査できる知的システム」を設計し、運用に乗せ、社会に対して責任を負うアーキテクトであること。Bootcamp の議論の端々で、この方向への合意が淡々と確認されていた気がする。

これは深い責任だと思う。モデルを呼び出すだけのシステムであれば誰でも作れる時代に、「なぜこの判断が出たのか」を説明し、「次にこう壊れたら、こう気づける」と保証することは、技術と倫理の両方を扱う仕事になる。業界として真剣に受け止めるべきテーマで、自分自身も腰を据えて取り組んでいきたい。

## Q&A で印象に残ったこと

カリキュラム本体と同じくらい価値があったのが、各セッション後の質疑応答の時間だった。とくに印象に残ったやり取りを、メモ的に短く触れておく。それぞれの詳細は該当する章で深掘りする。

- **Agent as Advisor 戦略** — Sonnet を主役にプロセスを駆動し、Opus は詰まったときの相談役として呼び出す。直感に反するこの構成のほうが、コストも品質も安定する場面が多いという。詳細は第3章で。
- **モデルアップデートと Eval の関係** — 新モデルへの乗り換えは、Eval スイートを"防衛線"として持っていない限り、リリースリスクに直結する。第6章で。
- **LLM-as-Judge のモデル選定** — Judge は強ければ強いほどよい、という直感は誤り。判定タスクの性質に応じて Haiku 〜 Sonnet を使い分ける視点が紹介された。第6章で。
- **Strands SDK との比較** — フレームワークの新しさで選ぶのではなく、何を制御したいかを起点に SDK を選ぶ。第3章で扱う。

## 教室での会話の価値

最後にひとつ書き残しておきたいのは、現地で交わした会話の濃さだった。隣に座った参加者は、まったく違う業界で似た悩みを抱えていて、休憩時間に「うちでは Eval をこう書いている」「Tool Description のレビュー会をこう運用している」という具体的な話を交換できた。

Bootcamp のカリキュラムは丁寧に設計されているが、それでも持ち帰ったものの半分くらいは、教室で偶然はじまった会話のなかから受け取った気がする。同じ時代に、同じテーマで、同じくらいの真剣さで悩んでいる人たちと2日間を過ごす経験そのものが、このプログラムの価値の少なくとも半分を占めていた、というのが帰国してからの率直な感想である。
